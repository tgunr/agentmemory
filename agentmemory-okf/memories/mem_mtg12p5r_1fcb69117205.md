Short answer: today, Hermes does **not** actually overlay a global config onto profile configs. So “global quick commands” don’t flow into profiles because there is no global base layer for them to inherit from.

## How it works today

The real config stack is:

```
DEFAULT_CONFIG  ←  profile config.yaml
```

- `~/.hermes/config.yaml` is treated as the **default profile’s** config, not as a global base.
- When you activate a named profile like `ollama`, Hermes resolves only:
  `~/.hermes/profiles/<name>/config.yaml`
- That file is deep-merged with the hardcoded `DEFAULT_CONFIG` only.
- The root `~/.hermes/config.yaml` is **not** read as a parent/base layer.

So if you define quick commands in the root config, a named profile does not see them, because it never loads that root file.

## Why all profiles can’t just use the global quick commands

Because inheritance isn’t implemented. Each named profile is effectively standalone. Anything you want in a profile must exist in that profile’s own `config.yaml` or in `DEFAULT_CONFIG`.

## What real layering would look like

If Hermes layered like VS Code, it would be:

```
DEFAULT_CONFIG  ←  ~/.hermes/config.yaml (global base)  ←  profiles/<name>/config.yaml (overlay)
```

In that model:
- global quick commands would be defined once
- each profile would inherit them automatically
- a profile would only need to override what it wants to change

## The catch

This layering behavior is **not implemented yet** in the current Hermes config loader. The skill I just checked captures the intended design, but as of now profiles do not inherit from the global config.
